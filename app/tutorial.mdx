<div id="what-is-keploy">

## What is Keploy?

</div>

Keploy is an **open-source, no-code testing tool** for backend developers. The pitch sounds almost too good:

- You run your app normally under Keploy.
- Keploy intercepts every call your app makes (to Redis, Postgres, external APIs — anything).
- Those intercepted calls get stored as **YAML test cases** you can replay any time.

No mocks to write. No fixtures to maintain. No test setup code. Your traffic is your tests.

<div className="arch-diagram">
  <div className="arch-diagram-title">How Keploy intercepts and replays traffic</div>
  <div className="arch-flow">
    <div className="arch-node arch-node-app">Your Go App<br /><small>(Gin)</small></div>
    <span className="arch-arrow">⟷</span>
    <div className="arch-node arch-node-keploy">🐰 Keploy<br /><small>(eBPF Agent)</small></div>
    <span className="arch-arrow">⟷</span>
    <div className="arch-node arch-node-redis">Redis<br /><small>:6379</small></div>
    <span className="arch-arrow">→</span>
    <div className="arch-node arch-node-storage">YAML Tests<br /><small>keploy/</small></div>
  </div>
</div>

It works using **eBPF** — a Linux kernel feature that lets Keploy hook into syscalls without touching your source code. That&apos;s the key: your app is completely unchanged.

## Step 7 — Sending Real API Traffic

</div>

In a **second WSL terminal**, I hit the API with curl to generate diverse test cases:

```bash
# Generate an OTP (captures the Redis SET command)
OTP=$(curl -s "http://localhost:3001/api/getVerificationCode?email=test@example.com&username=testuser" \
  | grep -o '"otp":[0-9]*' | grep -o '[0-9]*')
echo "Got OTP: $OTP"
```

```bash
# Correct OTP → 200 OK (captures Redis GET + token generation)
curl -i -X POST http://localhost:3001/api/verifyCode \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"test@example.com\",\"otp\":$OTP}"
```

```bash
# Wrong OTP → 500 (captures the failure path in Redis)
curl -i -X POST http://localhost:3001/api/verifyCode \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","otp":1}'
```

```bash
# Missing field → 422 (captures validation failure before Redis)
curl -i -X POST http://localhost:3001/api/verifyCode \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com"}'
```

## Understanding the YAML Test Files

</div>

After recording, Keploy created this structure:

```text
keploy/
  test-set-5/
    tests/
      get-api-getverificationcode-1.yaml
      post-api-verifycode-1.yaml   ← HTTP 200
      post-api-verifycode-2.yaml   ← HTTP 500
      post-api-verifycode-3.yaml   ← HTTP 422
    mocks/
      mock-0.yaml                  ← All Redis commands
```

Here&apos;s what one test case looks like:

```yaml
version: api.keploy.io/v1beta1
kind: Http
name: post-api-verifycode-1
spec:
  req:
    method: POST
    url: http://localhost:3001/api/verifyCode
    header:
      Content-Type: application/json
    body: '{"email":"test@example.com","otp":2370}'
  resp:
    status_code: 200
    body: '{"status":"true","token":"eyJ...","username":"testuser"}'
  assertions:
    noise:
      - header.Date
      - body.token
```

<Callout type="info" title="Smart noise detection">
  Notice `body.token` is marked as noise. Keploy detected that the JWT changes on every run (it&apos;s time-signed) and automatically excluded it from comparison. I didn&apos;t configure this — Keploy figured it out by comparing multiple recordings.
</Callout>

<div id="what-just-happened">

## What Just Happened?

</div>

Let me walk you through exactly what Keploy did under the hood — because the simplicity on the surface hides some genuinely clever engineering.

### 🔬 Phase 1 — `keploy record` (Interception Layer)

When you ran `sudo -E env "PATH=$PATH" keploy record -c "./gin-redis"`, Keploy didn't just "start watching." Here's the precise sequence:

1. **eBPF program loaded into kernel** — Keploy injected a BPF program into the Linux kernel's syscall table. This program hooks into `read()`, `write()`, `connect()`, and `accept()` syscalls — the four primitives every network communication eventually reduces to.
2. **Process spawned** — Keploy launched `./gin-redis` as a child process. From gin-redis's perspective, it was running completely normally.
3. **Traffic redirection** — Keploy printed `Started ingress forwarding {"orig_port": 3001, "new_port": 45909}`. This means all inbound TCP connections to port 3001 were transparently redirected through Keploy's proxy first, then forwarded to the actual app. Your `curl localhost:3001` never spoke directly to gin-redis.
4. **Outbound capture** — When gin-redis tried to connect to Redis on port 6379, the eBPF hook intercepted the `connect()` syscall, captured the destination, and began recording every `write()` (command sent to Redis) and `read()` (response from Redis).

### 📸 Phase 2 — Each `curl` = One Atomic Test Case

| What curl did | What Keploy captured |
|---------------|----------------------|
| `GET /api/getVerificationCode` | Full HTTP request + response, plus the Redis `SET otp:{email}` command and its reply |
| `POST /api/verifyCode` (correct OTP) | Full HTTP 200 response, plus Redis `GET`, `DEL`, and the JWT generated |
| `POST /api/verifyCode` (wrong OTP) | HTTP 500 response — and the Redis `GET` showing the mismatch |
| `POST /api/verifyCode` (missing field) | HTTP 422 — and **zero** Redis calls, because the app failed validation before touching the DB |

That last row is the subtle one. Keploy captured the *absence* of Redis calls as part of the test. If a future code change accidentally triggers a Redis call during a validation failure, the test will catch it.

### 💾 Phase 3 — YAML File Generation

After `Ctrl+C`, Keploy wrote human-readable YAML. Each `.yaml` test file contains:
- **`spec.req`** — The exact HTTP request (method, URL, headers, body)
- **`spec.resp`** — The exact HTTP response (status code, headers, body)
- **`spec.assertions.noise`** — Fields to ignore during comparison (e.g., `body.token`, `header.Date`)

The `mocks/mock-0.yaml` file stored every Redis command as a serialized binary-safe RESP record. These aren't approximations — they're the wire-level bytes your Redis client sent, base64-encoded.

### ▶️ Phase 4 — `keploy test` (Replay Engine)

When you ran `keploy test`, Keploy did something deceptively simple but technically precise:

1. **Started gin-redis** again as a child process.
2. **Intercepted all outbound Redis connections** — when gin-redis tried to connect to Redis (which was stopped), Keploy's eBPF hook caught the connection attempt and returned responses from `mock-0.yaml` instead.
3. **Replayed each HTTP request** from the test YAML files against the running app.
4. **Compared responses** — status code and body were compared field-by-field, skipping any keys listed under `noise`.

All 4 tests passed. Redis was stopped the entire time. Your app didn't know.
